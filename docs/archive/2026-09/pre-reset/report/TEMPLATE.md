# 报告样式规范（report）— v1，2026-09-12 立

> 本文是 `docs/report/` 的风格基准。**先读本文，再写报告**；后续报告一律沿用本结构，
> 不要另起一套。新增章节可以，删减必填章节不行。

## 1. 命名与位置

- 目录：`docs/report/`
- 文件名：`{yyyy-mm-dd}-{标题}-report.md`（日期=报告成稿日，非缺陷引入日；标题 ≤ 20 字，中文，不含空格与斜杠）
- 一次分析一份报告，不追加到旧报告里；同一主题的续报用新日期新文件，并在「关联」里互相引用

## 2. 必备章节（固定顺序）

| 序 | 章节 | 必填 | 要点 |
|---|---|---|---|
| 0 | 元信息 | ✅ | 表格：报告日期 / 分析对象（仓库、commit、构建产物）/ 触发方式 / 执行者 / 结论一句话 |
| 1 | 结论摘要 | ✅ | 表格，一行一个发现：ID、严重度、状态、类型、位置 `file:line`、一句话影响 |
| 2 | 分析方法与证据链 | ✅ | 用了什么工具、按什么顺序收敛到结论；**每条结论可回溯到命令或代码行** |
| 3..n | 发现详情 | ✅ | 每个发现一章，章内小节顺序固定：现象 → 根因 → 影响面 → 复现 → 修复建议 → 验收清单 |
| n+1 | 次要观察 | ✅ | 表格；不展开但必须留痕（严重度低于主发现、或未验证） |
| n+2 | 不确定性与未验证假设 | ✅ | 明确写出「我没验证什么」，禁止把推断写成实测 |
| n+3 | 产物与复现物清单 | ✅ | 新增/未提交文件、临时脚本、日志路径；写清是否已落盘 |
| n+4 | 后续工作与建议排期 | ✅ | 按严重度给优先级与验收人/责任面 |
| 附录 | 环境快照 / 逐条复现命令 | ✅ | 命令要能原样复制执行；环境（OS、工具版本、构建 profile）要写清 |

## 3. 严重度定义（固定口径）

| 级别 | 定义 | 例 |
|---|---|---|
| P0 | 数据丢失/安全边界击穿/进程冻结或不可用；无规避手段 | 死锁冻结会话、token 泄漏导致远程控制 |
| P1 | 功能阻塞但有规避；或安全缺口需要复合条件才可触发 | 单条路径挂起、需要用户交互才能触发 |
| P2 | 行为错误、性能退化、可观测性缺口，不阻塞主流程 | 清理不彻底、日志噪声 |
| P3 | 卫生问题（风格、注释、死代码） | 未使用的函数、误导性注释 |

## 4. 证据等级（每条结论必须标注其一）

| 等级 | 含义 | 要求 |
|---|---|---|
| E1 | **实测复现**（真机/真实二进制/测试套件） | 必须附原始输出片段（原文粘贴，可截断但不得改写） |
| E2 | **代码实证**（逐行读通的调用链 / diff 归属） | 必须给 `file:line` 链，且给出「为何不可能有其他解释」 |
| E3 | **静态推断**（未运行、未读全） | 必须写进「不确定性与未验证假设」 |

> 反例（禁止）：把 E3 写成「已确认」；用「应该」「可能」代替复现步骤；只给结论不给命令。

## 5. 写作规范

1. 中文；结论先行；一节一主题，禁止流水账。
2. 所有代码引用写 `path/to/file.rs:LINE`（或 `L120-L140`），LINE 以「分析时的 commit」为准，并在元信息里写明该 commit。
3. 复现命令必须是可复制执行的原文；涉及环境隔离的命令要显式写出隔离手段（如重定向 `USERPROFILE` / `QAQH_DATA_DIR`），禁止让后来者对着真实用户数据根复现。
4. 修复建议给**最小 diff**；有加固方案就另起「加固」子节，并说明代价与风险。
5. 每个发现必须带「验收清单」：修好之后怎么证明修好了（可执行命令 + 期望输出）。
6. 破坏性操作、未提交改动、临时脚本一律在「产物与复现物清单」登记；不隐瞒副作用。
7. 不写没有证据的因果；引用他人猜测时标注为猜测。

## 7. 关联约定

- 与 `docs/buglist`、`docs/plan`、`docs/spec` 的关系：**report 是证据与结论的记录**，
  从 report 里拆出的待办进 `plan`，规格化后的设计进 `spec`，长期结论进 `memory`。
- 报告一经写入视为「当时快照」：后续修复**不得回改历史结论**，只能新增续报或在
  「状态」列旁标注修复信息（`P0 → 已修复 @{commit}`）。
