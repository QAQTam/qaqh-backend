## 2. ToolName

### 2.1 形状（v1 落地）

```rust
/// 工具规范名：唯一查找键 + wire 标识。
/// 内部为 newtype，构造即校验；Display/serde 均为扁平字符串（wire 不变）。
#[derive(Clone, PartialEq, Eq, Hash, PartialOrd, Ord, Serialize, Deserialize)]
pub struct ToolName(String);

impl ToolName {
    /// 校验：`^[a-z][a-z0-9_]*$`，长度 ≤ 64。失败返回构造错误（不 panic）。
    pub fn new(raw: &str) -> Result<Self, DescriptorError>;

    /// 结构化命名空间视图（解析 `__` 约定，不改变 wire）。
    pub fn namespace(&self) -> Option<Namespace>;

    pub fn as_str(&self) -> &str;
}

/// 命名空间：由 `__` 分隔的前缀段识别。
/// - 无前缀 → None（内置工具）
/// - `mcp__{server}__{tool}` → Some(Mcp { server })
/// - `lsp__{tool}` → Some(Lsp)
/// - 未来 `plugin__...` / `subagent__...` 沿用同一解析
#[derive(Debug, Clone, PartialEq, Eq)]
pub enum Namespace {
    Mcp { server: String },
    Lsp,
    Extension { id: String },
}
```

### 2.2 规则

1. **wire 不变**：`ToolName` 序列化即扁平字符串；现有 `mcp__{server}__{tool}` 约定原样保留（base spec §5.1 的规范化与碰撞规则继续生效）。
2. **结构视图只读**：`namespace()` 供 policy / loop / 展示层统一分流（等价于 grok 的 `ToolKind` 归一），
   **不参与查找**——查找键恒为完整字符串。
3. **`display_name`**（base spec §5.1 已定）与 `ToolName` 分离：前者是上游原名（展示用），后者是规范名。
4. **预留**：v2.0 若需要"结构化命名空间 + wire 映射表"（对齐 codex `ToolName{namespace,name}`），
   在 `Namespace` 上扩展即可，不改变本 newtype 的公开面。

### 2.3 与现有实现的关系

| 现有 | 目标 |
|---|---|
| `ToolHandler.key: String` | `descriptor.name: ToolName` |
| `DynamicTool.def.function.name: String`（`mcp__` 前缀拼接） | 同一 `ToolName::new` 构造路径 |
| `runtime::lookup_category(name)` 按字符串查 | policy 经 `namespace()` 分流 + descriptor 声明 |

## 3. ToolCapabilities（新增）

### 3.1 动机

当前 loop 的编排逻辑全在手工代码里：

- `TurnState.serial_call_ids` / `tool_call_order`——写-写依赖靠人肉维护；
- exec 的进度流是特例通道（`bounded_exec_progress_channel`）；
- 取消宽限没有声明（base spec §6.4 只说"有界时间内返回"，没有数值来源）；
- workspace 绑定靠 thread-local 隐式传递。

大厂对应物：grok `ToolCapabilities`（并发/scope/frame caps）、codex 并行编排器（`parallel.rs`）+ `ToolRuntime` trait。
**结论：编排决策必须由工具自声明驱动，loop 不再硬编码。**

### 3.2 形状（v1 落地，加入 `ToolDescriptor`）

```rust
/// 工具能力声明：驱动 loop 的并发/串行/取消/流式决策。
/// 与 category/risk 正交——后者是权限输入，本结构是编排输入。
#[derive(Clone, Debug)]
pub struct ToolCapabilities {
    /// 并发档位（默认 `Serial`——保守，迁移工具逐个放宽）。
    pub concurrency: Concurrency,
    /// 是否声明支持进度流（ProgressSink 非空时才可能收到帧）。
    pub streaming: bool,
    /// 观察到取消后承诺的有界返回时间（base spec §6.4 的数值来源）。
    pub cancel_grace: Duration,
    /// 是否幂等（重试/重放安全的依据；影响 exactly-once 与批内重试策略）。
    pub idempotent: bool,
    /// 是否 workspace 绑定（cwd 敏感工具必须为 true，执行器强制注入 workspace_root）。
    pub workspace_bound: bool,
}

/// 并发档位。
pub enum Concurrency {
    /// 可与同批任意工具并行（只读类默认目标）。
    Parallel,
    /// 与同批其它工具串行（默认；写类工具的保守档）。
    Serial,
    /// 独占整个批次（如 exec 长进程、process 管理、journal 重写）。
    Exclusive,
}
```

### 3.3 消费规则（loop 侧）

1. 批次调度器按 `concurrency` 分区：`Exclusive` 独占、`Parallel` 成组并发、`Serial` 依次执行；
   同一 `Parallel` 组内出现资源冲突（同文件写）时，由 policy 的 `extract_target_paths` 检测后降级为串行——
   **不再需要 `serial_call_ids` 的手工登记**。
2. `streaming == false` 时 loop 不建进度通道（删除 exec 特例判断）。
3. `cancel_grace` 参与超时/取消收割的等待上限（base spec §6.4 的"有界时间"取值）。
4. `idempotent == true` 的工具在恢复/重放路径允许重新执行；false 的一律以"已执行事实"为准（对齐 tool_outbox 语义）。

### 3.4 迁移注记

- `Concurrency` 默认 `Serial`：迁移期行为不变（现状即串行优先）；只读工具迁移时改 `Parallel` 并加并发测试。
- exec/process 迁移时标 `Exclusive`，替换现有的显式判断。
- 字段是加法扩展：`#[serde(default)]`，不影响 wire（capabilities 不进模型面，仅进内部 descriptor 与 telemetry）。

## 4. 执行边界契约（工具 ↔ loop）

### 4.1 现状（问题）

loop 的 `engine_tool.rs` 同时承担：准入编排（admit_batch）、线程派生（4MB 栈 OS 线程）、事件双发
（ToolStarted/ToolUpdated/TimelineTool*）、进度泵（drain_bounded）、取消收割（seal/backfill）。
**执行细节漏进了回合逻辑**——这正是 v2.0 要切断的耦合。

### 4.2 目标接口（v2.0 方向；v1 以内部接口逐步引入）

```rust
/// loop → tool runtime：执行一个批次。
pub struct ExecuteBatch {
    pub turn_id: String,
    pub round_num: u32,
    /// 已授权调用（v1：AuthorizedToolCall；v2.0：runtime 内完成 admit）。
    pub calls: Vec<AuthorizedToolCall>,
    pub context: BatchContext,
}

pub struct BatchContext {
    pub session_id: String,
    pub workspace_root: PathBuf,
    pub mode: AgentMode,
    pub permission_level: PermissionLevel,
    pub cancellation: CancellationToken,
}

/// tool runtime → loop：批次结果。
pub struct BatchOutcome {
    /// 与 calls 一一对应，每项都是终态（含 Cancelled/Error）。
    pub results: Vec<CallOutcome>,
    /// 需要用户裁决的阻塞交互（挂起来源）。
    pub pending_interactions: Vec<PendingInteraction>,
    /// 批次级 fatal（已按 base spec §11 规则 seal 对应 timeline 块）。
    pub fatal: Option<FatalToolError>,
}

pub struct CallOutcome {
    pub call_id: String,
    pub outcome: ToolOutcome,     // base spec §8.2
}

/// 阻塞交互：权限 / ask / plan——由 loop 决定挂起（YieldToUser）与恢复。
pub struct PendingInteraction {
    pub call_id: String,
    pub kind: PendingKind,        // Permission | Ask | PlanApproval
    /// 展示/裁决载荷（runtime 适配层负责投影到 wire）。
    pub request: serde_json::Value,
}
```

### 4.3 职责切分（契约核心）

| 职责 | 归属 | 说明 |
|---|---|---|
| 批次编排（并发分区、串行降级） | **tool runtime** | 由 `ToolCapabilities` 驱动（§3.3） |
| 执行细节（线程/超时/取消/审计） | **tool runtime** | loop 不再派生工具线程 |
| 事件与进度发射 | **tool runtime → Effect 通道** | 直发协议适配层；loop 不搬运、不双发 |
| 挂起决策（何时 YieldToUser） | **loop** | 只消费 `pending_interactions` |
| 恢复（裁决回传） | **loop → runtime** | `ResumeInteraction { call_id, decision }` |
| admit（v1） | loop 保留（base spec §2.2） | v2.0 迁入 runtime（对齐 codex `Approvable`） |
| 准入语义（凭证/沙箱/trust） | **tool-policy（qaqh-sandbox 方向）** | 见 `2026-09-19-qaqh-v2.0-前瞻设计-plan.md` §4 |

### 4.4 时序（v2.0 目标）

```text
loop:  turn.step()
         └─ tools.execute_batch(ExecuteBatch) ──► runtime
                                                   ├─ 调度（capabilities）
                                                   ├─ 逐调用：policy → 沙箱 → handler
                                                   ├─ 进度/展示/审计 → Effect 通道（直发）
                                                   └─ 返回 BatchOutcome
loop:  ├─ results → 回填 message store（lap 边界）
       ├─ pending_interactions → YieldToUser（挂起）
       └─ fatal → TurnFailed（块已 seal）
```

### 4.5 与 base spec §6.4 / §9 的衔接

- 超时/取消分类（`Timeout` / `Cancelled`）不变；`cancel_grace` 只提供等待上限数值。
- `ToolProgress` 仍是展示数据；`ProgressSink` 由 runtime 构造并注入 `ToolCallContext.progress`，
  sink 必须：有界（帧大小与频率上限）、可丢弃、不承载终态信息（终态只经 `ToolOutcome`）。
- v1 落地路径：先把上述类型作为 `tool_api` 的内部接口定义（不接生产），
  `engine_tool.rs` 现有路径原样保留；迁移批次完成后再把 loop 切到 `execute_batch`。

## 5. TypedArgs 归属与共享

1. **归属**：每个工具的参数/输出类型定义在其实现模块内（如 `read.rs` 的 `ReadArgs`/`ReadOutput`），
   由 `schemars` 派生 `JsonSchema`（base spec Q1 已决策）。
2. **共享参数类型**：跨工具复用的字段类型放 `tool_api::args` 公共模块——至少：
   `PathArg`（workspace 相对路径规范化）、`OffsetLimit`、`CommandArgs`（command/cwd/timeout_secs）、
   `PatternArg`（glob/grep 共用）。
3. **canonical 字段名**：`tool_api::args::field` 常量模块（`PATH` / `OFFSET` / `LIMIT` / `COMMAND` /
   `CWD` / `PATTERN` / `DESCRIPTION`）——schema、typed 反序列化、展示投影共用同一拼写，
   禁止各工具自造同义字段名（对齐 grok `tool_taxonomy::field`）。
4. **动态工具（MCP/LSP）**：raw schema 直通，不强制 typed（base spec §15 Q5 已定）；
   其参数在 `ToolCallContext` 内保持 `serde_json::Value`，但输出仍经 `ToolOutput` 投影。

## 6. 命名冲突与整合建议（评审项）

**问题**：`ToolOutput` 在两份草案中含义不同——

- base spec §8.1：`pub trait ToolOutput`（投影职责：`model_blocks` / `summary` / `display`）；
- 09-18 输出侧契约 §3.1：`pub struct ToolOutput<O> { status, payload, error }`（typed 容器）。

**建议（待评审拍板）**：

1. base spec 的 trait 更名 **`ToolProjection`**（其职责就是"投影"），语义不变；
2. `ToolOutput<O>` 作为 v2 typed 容器名保留；`ToolOutcome`（erased）与其关系为：
   `ToolOutcome::from(ToolOutput<O>)`——erased 给 runtime/审计，typed 给工具作者与 typed RPC；
3. 实施影响：09-15 plan 的 P1-① 与展示契约中的引用同步更名（纯重命名，无行为变化）。

## 10. 实施记录

### P1-① 类型骨架（2026-09-19 落地）

`crates/qaqh-workspace/src/tool_api/`（12 文件，~1.9k 行）：
`display / descriptor / capabilities / context / error / output / progress / typed / erased / boundary / args / mod`。

回退点均为单点重命名/常量。原 `tool_api.rs` 内容原样迁入 `display.rs`，既有路径经 re-export 不变。

### P2-① LegacyToolAdapter（2026-09-19 落地）

`tool_api/legacy.rs`：`LegacyToolAdapter`（实现 `ErasedTool`）+ `map_tool_result`
（`ToolResult` → `ToolOutcome` 的**唯一权威**，供后续 wire 适配器复用）。

映射决议：

| 项 | 决议 |
|---|---|
| `output` | `output_ref` 优先 → `ContentRef`；否则 `Json(data)` |
| `error.code` | legacy UPPER_SNAKE **原样保留**（`ToolErrorCode::from_legacy`，仅 crate 内部）；kind 由码表推导，未知码归 `Custom` |
| failure 缺 error | 合成（保 SDK 不变量；legacy `validate()` 不在生产路径强制执行） |
| `diff` | → `display.diff`（仅展示面，不进模型面） |
| `images` | → `ToolOutcome.images`（**本次为 spec 补缺**：原 §8.2 未定义图片落点） |
| `action` | 新契约无此概念，适配器填 `""`（legacy `{name}_{action}` 解析属 admit 侧） |
| workspace | legacy handler 仍读线程局部（`set_actor_context`）；适配器**不写**线程局部（沙箱化 P3+ 工作） |

验收对照（plan P2-①）：

- 五态覆盖 ✓（成功/错误/partial/backgrounded/cancelled 各有测试）；

取值规则（写表依据，逐项核对）：

- `Parallel` ⇔ 纯只读（category ∈ {Read, Net}）且无共享可变状态；
- `Exclusive` ⇔ 派生进程组（exec/process）或批量重写文件（journal replay）；
- `streaming` ⇔ 真实产生进度帧（现状仅 exec——唯一消费 `tx_progress` 的 handler）；
- `idempotent` ⇔ 纯读取（重放不改本地状态；对齐 tool_outbox「已执行事实」语义）；
- `cancel_grace`：1s = 进程内 IO 边界轮询；5s = 进程组/批量重写（spec Q7 兜底，
  迁移时按实际收割路径标定）；
- `workspace_bound`：非绑定白名单 = {ask, todo_*, web_fetch}。
