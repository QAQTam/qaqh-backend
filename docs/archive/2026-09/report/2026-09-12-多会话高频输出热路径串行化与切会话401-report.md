### 3.1 现象

磁盘旁证（`%USERPROFILE%\.qaqh\ringing\journal`）：40 个 jsonl 文件合计 **27.1 MiB**，最大单文件 **4.79 MiB**（`conversation/ac578ae3.jsonl`），且恰好多次停在 4 MiB 阈值附近——即「写完就重写」的锯齿。

### 3.2 根因（E2）

`publish_with_causation` 在 `hub.rs:525` 取得全局 `channels` 锁（`guard`），该 guard **活到函数末尾**（`st` 借用自它）；而 `persist_append`（`:572`）与 `rewrite_if_oversized`（`:589`）都在其中：

```
crates/qaqh-runtime/src/ringing/hub.rs
:525   let mut guard = self.channel_state(channel);      ← 全局 Mutex（所有会话共享）
:526   let st = self.seed_state(&mut guard, channel, seed);
:567   match delivery {
:568     Delivery::Reliable => {
:569       match st.journal.append(&envelope) {
:572         AppendOutcome::Appended => { self.persist_append(channel, seed, &envelope);  ← 锁内磁盘 I/O
:589                                self.rewrite_if_oversized(channel, seed, st, false); ← 锁内全量重写
:636       self.fanout(channel, &envelope);
:666   }                                                   ← guard 在此才释放
```

`persist_append` → `JournalStore::write_line`（`journal_store.rs:370-386`）：

```rust
let file = self.file(channel, seed)?;
let mut line = serde_json::to_vec(op).map_err(io_error)?;   // 锁内 JSON 序列化
line.push(b'\n');
file.write_all(&line)?;                                     // 锁内 write 系统调用
file.flush()?;                                              // 锁内 flush（std::fs::File 为 no-op）
```

而 `rewrite_if_oversized`（`hub.rs:847-882`）在阈值到达时执行 `store.rewrite(...)`（`journal_store.rs:165-204`）：`self.files.remove(...)` → 全量 `serde_json::to_vec` 重建 body → `std::fs::write(tmp)` → `remove_file` → `rename`。注意 `hub.rs:817` 的注释写着「持久化钩子：I/O 失败只记录日志，**绝不阻塞事件路径**」——与代码事实矛盾（**次要观察 O-1**）。

**关键前提**：`RoundDelta`（每 token 的流式增量）的 delivery 是 **`Reliable`**，不是 replaceable：

```rust
// crates/qaqh-domain/src/event.rs:429-438
impl ConversationEvent {
    pub fn delivery(&self) -> Delivery {
        match self {
            ProviderToolStatus | UsageUpdated | CompactProgress | BlockCheckpoint => Delivery::Replaceable,
            _ => Delivery::Reliable,          // ← RoundDelta 落到这里
        }
    }
}
```

于是**每一个 token** 都会走一次「锁内序列化 + 锁内 write」，并且在累计 ~4 MiB 时触发一次**跨所有会话**的停顿式全量重写。

### 3.3 影响面

| 维度 | 说明 |
|---|---|
| 跨会话串行 | `channels` 是**单把** `Mutex`，`hub.rs:525` 的 guard 覆盖磁盘 I/O。会话 A 的一次 4 MiB 重写（实测 34 ms）期间，**会话 B/C 的每一个事件发布都被阻塞**——多会话并行度被压回单核单线程 |
| 反直觉的「输出越快越慢」 | 事件速率越高 → 4 MiB 阈值越快到达 → 全量重写越频繁 → 每次重写冻结所有会话的 11–34 ms × 每秒次数。这是「API 输出速度过快」直接放大症状的**唯一**机制 |
| 反向背压到模型 | 发布会话线程是每会话一个 OS 线程的 event reader；它卡在 `channels` 锁上时，上游 `PacedEmitter::emit_domain` 的**有界** `sync_channel(16384)` 会填满 → **阻塞 agent 循环线程** → 停止向 provider 取流 |
| 与文档不符 | `persistence_policy.rs:17` 与 `hub.rs:1410` 注释均称 `RoundDelta` 是「覆盖式 / replaceable」，代码是 `Reliable`（**次要观察 O-2**）——成本模型被文档低估 |

### 3.5 修复建议

**最小 diff（消掉锁内 I/O，不改语义）**：

1. `journal_store` 改为**单写线程 + 有界队列**：`persist_append` 只做 `try_send`，序列化与 `write_all` 移出 `channels` 锁（`hub.rs:572`、`:589` → 投递）。代价：崩溃窗口从「0」变为「队列深度」，需在 `flush_timeline_persistence` 同位置加 drain。
2. `rewrite_if_oversized`（`hub.rs:847-882`）的 `file_size` 与 `rewrite` 移出 `channels` 锁：先在锁内**只做 `pending_bytes` 判定并置标志**，重写在锁外由写线程完成。
3. `channels` 由「单把全局 Mutex」改为 **per-(channel,seed) 锁表**（`hub.rs:196` 的 `lazy_loads` 已是现成范式）——这一条同时消掉 D-5 的跨会话串行。

**加固（成本递增）**：

4. 重新评估 `RoundDelta` 的 delivery 级别：若前端已支持 `BlockCheckpoint` 覆盖语义（`event.rs:350-361` 注释称 checkpoint 是 replaceable、可自愈丢 delta），则可把 `RoundDelta` 降为 `Replaceable`，直接把「每 token 一次落盘」变成「每 64 token 一次」。
5. `JournalOp::Append { envelope: envelope.clone() }`（`journal_store.rs:85`）避免整信封二次克隆。

## 4. 发现 D-2：`BlockCheckpoint` 全量文本 → 单次发布成本随块线性增长；`TurnSealed` 同步全量重写

### 4.1 现象

生产 timeline 快照体积远超回合数应有的规模：`ringing/ringing-timeline/` 下 12 个文件，最大 **17.07 MiB**（`a6227e42.json`），其次 6.53 MiB、5.62 MiB；而对应会话的 `messages.jsonl` 只有 0.83–4.03 MiB。

### 4.2 根因（E2 + E1）

`BlockCheckpoint` 携带该块**当前完整文本**（`event.rs:350-361`），且被判为「进快照持久层」：

```rust
// crates/qaqh-runtime/src/ringing/persistence_policy.rs:62-75
pub fn is_snapshot_persisted(event: &qaqh_domain::TimelineEvent) -> bool {
    matches!(event,
        TimelineEvent::TurnOpened { .. } | TimelineEvent::BlockOpened { .. }
      | TimelineEvent::BlockCheckpoint { .. } | TimelineEvent::ToolUpdated { .. }
      | TimelineEvent::BlockSealed { .. } | TimelineEvent::RoundSealed { .. }
      | TimelineEvent::TurnSealed { .. })
}
```

每次 checkpoint 都要把全量文本写回内存投影（`timeline.rs:471` `apply_intent` 的 replaceable 覆盖语义），因此**单次发布成本 = O(块文本长度)**。实测（`%TEMP%\qaqh-bench`）：

```

checkpoint    4 KiB      n=100    mean=  0.002ms
checkpoint   32 KiB      n=100    mean=  0.017ms
checkpoint  128 KiB      n=100    mean=  0.129ms
checkpoint  512 KiB      n=100    mean=  0.396ms
checkpoint 1024 KiB      n=100    mean=  0.859ms
checkpoint 2048 KiB      n=100    mean=  1.718ms
checkpoint 4096 KiB      n=100    mean=  3.310ms
```

**严格线性**。以真实长块（累积到 4 MiB 不罕见）计，checkpoint 节流是 64 token / 2 s（`gate.rs:19-21`），即 **每 1–2 秒一次、每次 1–3.3 ms**，且这段成本发生在**持有 `timeline` 全局锁**的 `apply_intent` 内。

`TurnSealed` 更重：`publish_timeline`（`timeline_hub.rs:372-381`）判定 terminal 后调用 `persist_timeline_sync`（`:391-440`），它**同步**执行「取快照深拷贝（`timeline.rs:663-678` `turns.values().cloned()`）+ `replay_since` 全量克隆 + 审计追加 + `TimelineStore::persist` 全量序列化与原子替换」，全程持有 `timeline_store` 锁，且**在发布事件的那个线程上**（会话 event reader）。实测：


按生产 17.07 MiB 快照外推 ≈ **30 ms/回合结束**；而日志显示存在单会话说 `round_num` 达 **142** 的回合。

此外，1 Hz 的异步 checkpoint 线程（`timeline_hub.rs:52-124`）同样在持 `timeline_store` 锁期间做 `snapshot()` 深拷贝 + 两次 `replay_since` 全量克隆（`:75`、`:79-86`）——**每个活跃会话每秒一次**，且这些克隆都在**全局 `timeline` 锁**内完成，所有会话的 timeline 发布都要排队等它。

### 4.5 补充发现 D-6：journal 驱逐的 O(n) 悬崖（与 D-2 同源）

`TimelineAppender` 的内存回放尾用 **`Vec` + `remove(0)`** 做头部驱逐：

```rust

    let entry_limit = /* persistence_policy.rs:32 = 8192 */;
```

### 5.4 为什么「输出越快」会促成 401

`ConcurrencyLimitLayer(128)` **不是**原因：`Router::layer` 按路由（MethodRouter 再按方法）逐个套用，且 tower 的 permit 随响应 future 完成即释放，SSE 长连接不占用（已由 subagent 核对 tower 0.5.3 / axum 0.8.9 源码，**推翻了本分析早期的假设**）。真正的促成路径是**一条正反馈回路**：

```
输出变快
  → hub.publish 事件率上升 → channels 全局锁内在途变长（D-1，8 会话聚合吞吐反而 -35%）
  → 频道/timeline broadcast（每频道单环 1024、timeline 全进程单环）被任一会话填满
      ※ 连接在 recv 之后才按 seed 过滤：任一会话变快会把所有连接（含空闲会话）推向 Lagged
  → SSE task 卡在 mpsc(128) 的 send → 停止排空 → Lagged → break（响应体干净结束）
  → 客户端把 EOF 当错误 → 重连（带 Last-Event-ID）
  → 重连走「订阅→回放→过滤」，而 filter_replay_for_session 在【一次】全局租约锁里做 R 次 owns_seed
      实测单次持锁：62.4 ms @(L=200, R=8192)，247 ms @(L=200, R=32768)
  → 持锁期间 renew / commands / bootstrap / service / 所有会话的每事件租约锁全部排队
  → renew 被拖过 30 s TTL → expire() 连带清 seed 归属 → 401
  → 更多 Lagged → 更多重连（回到上一步）
```

两处 D-3 之外的量化事实（独立 micro-bench，E1）：

- `owns_seed` 内含 `expire()` 且每次调用**分配一个 HashSet**：租约数 L=1 → 0.20 µs，L=200 → **7.00 µs**（35×）；`is_active_session` 同为 O(L) 全表扫描。SSE 每事件每连接取 1–2 次 → 12 连接 / L=200 时 p99 **563 µs**、max **31 ms**。
- 重连回放的持锁时间**随总租约数线性增长**（L=1 时 8.58 ms @R=32768，L=200 时 247 ms）——即**历史会话越多，重连风暴的全局停顿越长**。

**关于客户端退避的一处更正**：`qaqh-client` 的 `run()` 只在 `Err` 分支 sleep/double（`sse.rs:62-85`），而 `connect_once` 对「响应体干净结束」返回 **`Ok(())`**（`timeline.rs:100-106` 与 `sse.rs:63-66`）→ **clean EOF 不睡、立即重连**；更糟的是 `retry_ms` 在成功连接时**永不复位**（`sse.rs:83`、`timeline.rs:144`），一旦因任何错误涨到 30 s，此后所有重连都固定等 30 s。两个缺陷叠加：断流瞬间进入**紧密重连风暴**，风暴本身把 `retry_ms` 推高，随后退化为**每 30 s 才补一次帧**——前端主观感受正是「文字不动 / 越用越卡」。


### 5.5 修复建议

**最小 diff（让 attach 快且先于副作用）**：

1. `command.rs:440-459`：把 `attach_seed` **提到** `service.handle("session.resume")` **之前**（当前先拉起 worker 再 attach，制造窗口）；并把三处被忽略的 `attach_seed` 返回值（`command.rs:418-432`、`:455-459`、`:485-489`）改为显式 401。或者：把 `Client::attach`（`client.rs:427-436`）从 `SessionResume` 改为 `SessionAttach`（daemon 侧是纯 lease 拦截，`command.rs:469-496`）。

**加固**：

3. `lease_store.rs:71-76` 去掉 `owns_seed` 里的 `expire()` 副作用（改惰性判断 + 独立 GC）；`owns_seed` 同时要求活跃性；`open()` 覆盖同 instance id 时清掉旧 cs 的 `seed_leases`。
