## 事实与证据

### 因果链（每一环都有 file:line）

| # | 事实 | 位置 |
|---|---|---|
| 1 | daemon 每 **15s** 发一次 SSE keepalive | `qaqh-daemon/src/axum_server/axum_impl/sse.rs:478-481`（`KeepAlive::new().interval(Duration::from_secs(15)).text("keep-alive")`） |
| 2 | 客户端把它当**注释行丢掉** | `qaqh-client/src/sse_decoder.rs:105`（`continue; // 注释行（keepalive）`） |
| 3 | 但它**重置了客户端的 45s 空闲计时器**（字节到了） | `qaqh-client/src/sse.rs:175`、`timeline.rs:275` |
| 4 | ⇒ 流**永不空闲 ⇒ 永不重连** | 重连只在出错/空闲超时/epoch 变/租约重协商时发生 |
| 5 | ⇒ `ChannelStatus::Open` **永不再发**（它只在连接建立那一刻发一次） | `qaqh-client/src/sse.rs:142` |
| 6 | ⇒ TUI 的 `last_open` **只在建连时被记过一次**，此后再也不动 | TUI `src/runtime.rs` 的 `on_status` 分支 |
| 7 | ⇒ 看门狗量的是「连接建立了多久」而非「多久没听到 daemon」 | TUI `src/runtime.rs:323`（`last_open.elapsed() > STALL_AFTER`） |

**净效果**：任何活过 `STALL_AFTER` 的连接都被判失联，**与有没有数据无关**；而且一旦
误判就永久停在 `✗ lost`——因为能复位它的路径（重连 → `Open`）恰好被 keepalive 堵死了。
现象即机主所述：**后端在干活、前端在输出，状态栏却一直 `✗ lost · Ctrl+R 重连`**。

### 归因纠正（值得记下来）

首轮归因写的是「**越活跃越像失联**」——那个说法把**遮蔽效应**当成了**成因**：

- 「忙」并不是判据的一部分，判据从头到尾没看过数据；
- 「忙」只是**挡住了那条偶然的自愈路径**（空闲流本会在 45s 空闲超时后重连并复位）。

机主追问「daemon 怎么会忙？」后重查才发现第 1、2 环。**教训**：当解释需要引入
「对方很忙」这类外部条件才能成立时，先怀疑判据本身量的东西不对。

### 为什么它在 harness 里一直没被发现（重要）

`scripts/e2e-restart.sh` 的每次输出里**都带着这个症状**：

```
| ◌ 已断开 ✗ lost · Ctrl+R 重连 与 daemon 失联（15s 内无任何频道连接）——按…
```

而被读成了**预期行为**——因为该 harness 的动作正是「杀掉 daemon」，所以「失联」
看起来理所当然。**一个只在「对方确实死了」时才该出现的提示，与「对方活着也出现」
在同一个场景下无法区分**，除非你去跑一个「对方活着」的对照场景。

harness 本身也因此掩盖了它：它只覆盖「真死 → 失联 → 重连」这条路径。

## 处置

### 正确信号一直都在线上，只是没人接

daemon 发 keepalive 的**本意**就是「我还活着」；客户端把它丢掉后没有任何出口。

**`qaqh-client`（`d9fa81c`）**：`ClientHandlers` / `StreamHandlers` / `TimelineStream`
各增 `on_liveness: Arc<dyn Fn()>`，在两条 SSE 读取循环里**每消费一个 chunk 调一次**
——**在解码之前**，因为 keepalive 会被解码器丢掉，而那正是要报的东西。

**TUI（`2ff0351`）**：接线 `on_liveness` → `note_daemon_activity()`；`STALL_AFTER`
**60s → 20s**（= keepalive 间隔 15s 留一轮余量）。

语义由此闭环：

| 情况 | 结果 |
|---|---|
| daemon 活着（哪怕完全空闲） | keepalive 每 15s 确认一次 → 永不误报 |
| daemon 真死 | 字节断流 → 20s 后判定失联 ✓（灵敏度与最初的 15s 相当） |

### 一次被自己推翻的中间版本（如实留档）

首版修复是 `85fec70`：只在 `on_batch` / `on_timeline_entry` 上复位时间戳，并把
`STALL_AFTER` 提到 60s。**它只修好了「忙」的那一半**——空闲会话只有 keepalive、
没有批次，60s 后照样误报，只是把 15s 拖成了 60s。60s 那个值是为绕开误报而做的
妥协，正确信号接上后已撤回。`2ff0351` 同时移除了那些重复接线，避免「哪个信号才是
权威」变模糊。

### 验证

harness 重跑（`scripts/e2e-restart.sh`，时间线随 `STALL_AFTER` 重标）：
`◌ connecting → ● ready e60ac803 → ✗ lost → ● ready 945bef09` ✓ 两次 ready 且 epoch 不同。

**验证边界（如实说明）**：「空闲/忙流不再误报」**没有自动化覆盖**——它需要一个
「daemon 活着且持续会话」的对照场景，而那正是上面第「为什么没被发现」一节指出的
harness 盲区。该场景由机主直接跑确认。**补一条对照 harness 是此条目的未竟事项。**

### 一条需要记住的不变式

**「收到字节」是唯一可靠的存活证据，而它必须由客户端在解码层之前报出来。**
任何「仅由状态转换驱动」的存活判据都会漏掉「连接一直健康」这个最常见的情形——
健康恰恰意味着没有状态转换。
