## 0. 一句话

**把「结构」和「环境能力」从历史里解耦出去，只让对话事实留在 canonical log。**

## 1. 三个问题的共同根因

| # | 现象 | 根因 | 证据 |
|---|---|---|---|
| A | 中途 `push_system` 会把新内容顶到整个前缀最前，从第一个字节起 cache 全 miss | 前缀没有显式分区，只有一个按**插入顺序**排列、渲染时**永远前置**的 `system_messages: Vec<Message>` | `store.rs:531`（`push_system`）、`store.rs:991`（`build_context_for_gate` 先 `v.extend(system_messages.clone())`） |
| B | 压缩结果被物化成第二个真源；请求峰值内存 2× | `compact-context.json` 持有整个活跃窗口的副本，且每次 append 后重写 | `manager.rs:1402`、`manager.rs:569`（`update_compact_context`：`context.messages = messages.to_vec()`）、`store.rs:991`（整段 clone） |
| C | MCP 清单变化往历史追加 developer 消息，历史增长 + cache 断点 | MCP 资源清单被当成「对话事实」注入历史 | `agent.rs:719`（`sync_mcp_resource_injection`）、`engine_turn.rs:1422` |

三者是同一个主题：**结构（前缀分区）、派生状态（压缩结果）、环境能力（MCP）都被塞进了「历史消息」这一种表达里。**

## 2. 设计输入 A：前缀用 `Segment` 分区，不用 msg_id 槽位

### 2.1 现状

- `MessageStore.system_messages: Vec<Message>` 只按插入顺序排，渲染时永远前置。
- 但 `push_system` **也**调用 `save_msg`，所以 system 消息会拿到一个**写入序** `msg_id`。
- 结果：system 消息的 msg_id 表达「写入时间」，位置却表达「永远最前」——两个语义打架。
- 会话跑到第 10 轮激活 skill → 新 system 消息拿到高位 msg_id，却插到最前 → 前缀整体失效。
- 已有诊断：`PrefixShape { system_hash, tools_hash, msg_hashes }`（`agent.rs:68`），能报「第 i 条消息变了」，但报不出「是哪个语义段变了」。

### 2.2 明确否掉的方案：把 msg_id 0/1/2 当固定槽位

曾考虑：`msgid 0 = system prompt（不可变）`、`msgid 1 = MCP`、`msgid 2 = skills`、user 从 3 起。**否掉**，理由：

1. **`msg_id` 的语义是写入序/全序，不是逻辑槽位。** 代码把用途写死了：`msg_id` doubles as the store's write sequence，`flat_in_write_order` 用它按 arrival order 合并 turns + trailing（`store.rs:279`、`store.rs:968`）。预留低号会和这个语义打架。
2. **`messages.jsonl` 是 append-only。** 槽位内容可变 = 原地改历史，需要发明 tombstone/覆盖语义；`from_messages` 的既有规则是「前导 system 收进 system_messages、中段 system/developer 恢复为 trailing、其余静默丢弃」（`store.rs:1334`）。
3. **哨兵冲突。** `msg_id: Option<u64>` 的 `None` 已经是「未分配（ephemeral/subagent）」，`next_msg_id` 从 1 起（`store.rs:244`）；再引入 `0 = 特殊槽位` 是第二套哨兵。
4. **粒度对不上。** N 个 MCP server / M 个 skill 装不进一个固定号。
5. **不解决问题。** prefix cache 是**最长公共前缀**；把会变的内容放进「不可变前缀」，只是把 miss 从「中段」提前到「开头」。

### 2.3 目标形态

引入显式分区标签（字段名待定）：

```rust
enum Segment {
    Base,         // 不可变 system prompt
    Skills,       // skills 激活集（易变，但属于对话意图）
    Environment,  // 环境注解（= 现在的 frozen_annotation）
    History,      // user / assistant / tool
}
```

规则：

1. **组装顺序**由 `Segment` 的固定优先级决定：`Base → Skills → Environment → History`。
2. **段内顺序**仍由 `msg_id` 决定（`flat_in_write_order` 不动，全序语义保留）。
3. **append-only 保持**：段内容变化时**追加**一条 `SegmentUpdated { segment, revision, ref }` 记录，读侧取每段最高 revision；**不原地改历史**。
4. **不可变性靠冻结，不靠槽位**：`Environment` 段即现在的 `frozen_annotation`（P0 cache fix：持久化以保跨重启 byte-identical）。
5. **诊断按段**：`PrefixShape` 从「第 i 条消息变了」升级为「第 X 段变了 + 段内第 j 条变了」。

### 2.4 关键判断

- **`Segment::Mcp` 不该存在**（见 §4）。
- `Skills` 保留为独立段是合理的：它是「用户显式激活」的语义，属于对话意图，现有 `Preserved`（压缩后仍在）策略正确。

### 2.5 验收

- 中途注入新 skills envelope → **前缀 `Base` 段 hash 不变**，只有 `Skills` 段变化。
- 重启后 `Base` / `Environment` 段 hash 与重启前一致。
- `PrefixShape` 能定位到具体段。

## 3. 设计输入 B：compact 作为 canonical fact

### 3.1 现状

| 产物 | 角色 |
|---|---|
| `messages.jsonl` | **不可变归档**，压缩从不重写它（`manager.rs:542` 注释） |
| `compact-context.json` | **LLM 面视图**（摘要 + 保留段），独立文件（`manager.rs:1402`） |
| `meta.compact_skip` | 被跳过的最早 turn 数 |

压缩摘要本身是一条**合成消息**：`apply_compact` 构造 `[Compacted N turns]` 的 user 消息，**复用被压缩首 turn 的 msg_id** 插回去（`store.rs:1590-1598`）。

### 3.2 问题

1. **第二个真源。** `compact-context.json` 持有整个活跃窗口的副本，`update_compact_context` 在每次 append 后重写它（`manager.rs:569`）。spec 的 D3「投影不持久化为事实」在这里被违反。
2. **请求峰值 2×。** `build_context_for_gate` 每轮 `system_messages.clone()` + `flat_in_write_order()` 整段 clone（`store.rs:991`）。
3. **内存已是有界的，别误判。** `evict_compacted_prefix()` 会把被压缩前缀 `turns.drain(0..n)` 掉（`store.rs:491`、`lifecycle.rs:237`）。**问题不是「内存没驱逐」，是「压缩结果被物化成 side file」。**
4. **摘要身份是伪造的。** 它借用被压缩首 turn 的 msg_id，语义上是「一条假装成历史的消息」。

### 3.3 目标形态

把压缩做成 canonical fact：

```
ContextCompacted {
  compact_id,
  covered_msg_ids: [..],     // 被摘要覆盖的范围
  summary_ref: ContentRef,   // 摘要正文，内容寻址，不常驻
  kept_from_msg_id,          // 保留段起点
}
```

context 拼装 = `读 canonical log → 找最后一个 ContextCompacted → summary + 从 kept_from_msg_id 起按 msg_id 拼`。

**`compact-context.json` 删除。** 这正好落在 P6 第 1 条「删除旧目录 / 独立快照 / 重复存储」上。

### 3.4 内存边界（必须说清，别承诺过头）

- **请求时必须 materialize 完整 context 成 JSON body**，这一步省不掉。
- 能省的：① 请求**之间**不常驻（现在常驻）；② 峰值 **2× → 1×**（去掉 `build_context_for_gate` 的整段 clone，改迭代器/借用或流式序列化）。
- 大内容继续走 `ContentRef` 外置按需读盘——机制已有（`ContentBlock::ImageRef` + `content_store`），往 tool result 扩展即可。
- **不要**每轮从磁盘重读+反序列化活跃窗口（O(窗口) IO+解析）。务实做法：内存留活跃窗口的轻量索引（msg_id + 偏移），正文按需读；或让活跃窗口常驻（它本来就被 compaction 限界）。

### 3.5 验收

- 删除 `compact-context.json` 后，重启恢复的 context 与删除前**字节等价**。
- 压缩前后 `messages.jsonl` 不被重写（append-only 断言）。
- 请求峰值内存相对现状下降（以 `build_context_for_gate` 不再整段 clone 为判据）。
- `summary_ref` 缺失/损坏时 fail-closed（对齐现有 BUG-007 语义：不回落全量归档）。

## 4. 设计输入 C：MCP 不进历史

### 4.1 现状是两层，别混

**工具面（tools）——不在上下文里：**

- 每个 server 的 `tools/list` 投影成 `mcp__<server>__<tool>` 原生动态工具，注册进 `ToolManager`。
- 时机：**每回合边界** `clear_dynamic` + 逐条 `register_dynamic`（全量重建，`engine_turn.rs:1404`）。
- 所以「工具目录」= **tools 数组**，每回合重建 → 天然最新，**不占历史**。
- 另有聚合工具 `mcp`：`list_servers` / `list_resources` / `read_resource` / `list_prompts` / `read_prompt`。

**资源面（resources）——这个才注入历史：**

- `resource_env_block()` 生成资源清单摘要（server + resources + templates），**封顶 `ENV_BLOCK_MAX_ITEMS = 20`**，超出打 `…(truncated at 20 items)`（`resources.rs:379`）。
- 作为 **trailing developer 消息**注入，**内容比对门控**（`agent.rs:719`：`if self.last_mcp_env_block.as_deref() == Some(block.as_str()) { return; }`）。
- `Compressable`：压缩后下回合边界重新注入最新版。

### 4.2 决定性证据

1. **`list_resources` 是本地缓存读取，不是网络往返。** 注入侧读 `conn.cached_resources()`；工具侧 `list_resources` 读**同一个** `conn.cached_resources()`（`resources.rs:182`）。省这一次 tool call 的收益 ≈ 一次本地函数调用。
2. **注入的是截断的，工具返回的是完整的。** 注入封顶 20 条；`list_resources` 无此上限。
3. **注入成本实打实。** 每次清单变化 → 历史追加一条 developer 消息 → 不可回收增长 + prefix cache 断点。

> 结论：**注入的是一份「被截断的、可能过期的、占历史的」副本；模型按需查能拿到完整且实时的。**

### 4.3 目标形态

1. **`sync_mcp_resource_injection` 默认关闭**，由 `[mcp].inject_resource_env_block`
   控制（`#[serde(default)]` → **false**），保留代码路径与测试作 opt-in。
2. **`mcp` 工具 description 动态化**：带 server 数量/名称 + 「资源用
   `list_resources` 查」。description 在 tools 数组里，随 `tools_hash` 变化，
   **不进历史**。
3. `resource_env_block` 渲染逻辑保留（仅服务于上面那个 opt-in 开关）。注意它与
   `mcp list_resources` 是**两套独立渲染**，不是复用关系——`list_resources` 走
   `## server` 分节、无 20 条封顶。
4. **明确否掉「只在启动注入一次」**：同时拿到「过期」（server 重启后 resource
   变了模型不知道）和「占历史」两个缺点，不如不注入。

### 4.5 已落地（2026-09-24）

- `qaqh-types::PersistentMcpConfig.inject_resource_env_block: Option<bool>`、
  `qaqh-config::McpConfig.inject_resource_env_block: bool`（缺省 false）。
- `qaqh_mcp::resource_env_block_with` 在 `enabled && inject_resource_env_block`
  两个条件都成立时才产出块。
- `aggregate_entry(cfg, timeout)` 的 description 改为动态：零 server 时明说
  「No MCP servers are configured」并指向 `list_servers`；有 server 时列出
  `N MCP server(s) configured: <BTreeMap 有序名单>` 并指向 `list_resources`。
- 测试：`qaqh-config`（默认 off + TOML opt-in）、`qaqh-mcp`（有缓存资源但注入
  关闭 → `None`；description 携带 server 名单）、`qaqh-runtime`（注入路径本身，
  显式打开）。

### 4.4 验收

- MCP 清单变化时：**历史长度不变**、`tools_hash` 变化。
- 关闭注入后 `mcp list_resources` 仍能返回完整清单（含 templates）。
- `PrefixShape` 不再出现 MCP 相关的 `msg_hashes` 变化。

## 6. 明确否掉的方案

| 方案 | 否掉理由 |
|---|---|
| msg_id 0/1/2 当固定槽位 | §2.2：借错字段、破坏写入序、需原地改 append-only 日志、粒度对不上、不解决 cache 问题 |
| 按 role 优先级排序（system→user→developer→tool→assistant） | provider 协议硬约束：assistant `tool_use` 必须紧跟 `tool_result`；thinking+text+tool_use 必须同一条 assistant message；role 只能当标签 |
| 「只在启动注入一次 MCP 清单」 | 同时拿到「过期」+「占历史」两个缺点 |
| 每轮从磁盘重读整个活跃窗口 | O(窗口) IO+解析，长会话每轮做不划算 |
| 承诺「上下文完全不驻留内存」 | 请求时必须 materialize 成 JSON body，做不到；只能做到「不常驻 + 峰值 1×」 |
