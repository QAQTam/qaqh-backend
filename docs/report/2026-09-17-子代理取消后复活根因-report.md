# 子代理被判定 cancelled 后「复活」——根因报告（2026-09-17）

> 状态：**已定位根因**（证据自足，含 daemon 实机日志铁证）。
>
> 现象：TUI 与后端**都**已把某个 subagent 判为 `cancelled`，随后它又活跃起来
> （继续产出事件 / 重新出现在时间线 / 重新进入跟踪集）。
>
> 结论：**这不是单一 bug，而是三个独立缺陷叠加成的「取消不可靠」链条。**
> 每一个单独看都「有理由」，叠加后产生「已取消的实体会重新活跃」的观感。

## 0. 一句话根因

**父会话取消时，取消信号既不传播到子 seed，也不被注入路径尊重**——
`collect_subagent_result` 在 cancel 后仍无条件向父会话注入结果，
而注入路径会 `clear_cancel()` 并开启新回合，于是「取消」只终止了子回合本身，
**没有终止「子代理结果回灌父会话」这条边**。

## 2. 根因链（三处缺陷）

### 缺陷 1：`spawn_subagent_inprocess` 不注册 liveness

`crates/qaqh-runtime/src/registry.rs:361`：

```rust
fn spawn_subagent_inprocess(&mut self, seed: &str, spec: SubagentSpawnSpec) -> Result<(), String> {
    if self.instances.contains_key(seed) { ... }
    self.last_spawn.insert(seed.to_string(), std::time::Instant::now());
    let (generation, _) = self.activity.begin(seed);   // ← 只有这个
    // …
    // 全文无 hub.mark_worker_live(seed)
}
```

对比另外两处 spawn 路径**都有**：

| 路径 | 位置 | 是否 `mark_worker_live` |
|---|---|---|
| `get_or_spawn`（普通会话） | `registry.rs:292` | ✅ |
| respawn（worker 死亡重拉） | `registry.rs:715` | ✅ |
| **`spawn_subagent_inprocess`** | `registry.rs:361` | ❌ **缺失** |

**后果**：`live_workers` 不含子 seed → `seal_orphan_channel_state` 的 liveness 门
（`orphan_seal.rs:83-92`）形同虚设：

```rust
if !force && self.live_workers.lock()...contains(seed) {
    log::info!("[ringing] worker alive for {seed}; skipping bootstrap orphan seal");
    return false;                     // ← 子代理永远走不到这里
}
```

这就是**现象 C**：子代理只要被请求一次 timeline（`timeline_api.rs:85`
无条件调 `seal_orphan_channel_state(&seed, false)`），就被当成孤儿封掉。

### 缺陷 2：取消后仍向父会话注入结果

`crates/qaqh-subagent/src/lib.rs:523-595`：

```rust
let (state_tag, header) = if did_cancel {
    ("cancelled", format!("subagent '{name}' cancelled"))
} else if exit_code != 0 { ... } else { ... };

if !parent_seed.is_empty() {
    // ← 无 did_cancel 判断，cancelled 也照样注入
    let inject = RingingCommand::Conversation(ConversationCommand::ConversationSendMessage {
        text: format!("<qaqh_subagent_result name=\"{name}\" state=\"{state_tag}\" ...>"),
        as_system: true,
    });
    // 5 次重试注入，成功即 accepted
}
registry_ref.finish(&final_answer, exit_code);   // L597
```

`did_cancel` 只影响 `state_tag` 文案，**不阻止注入**。

### 缺陷 3：注入路径主动清除取消标志并开启新回合

`crates/qaqh-runtime/src/agent/engine_input.rs:261-262`：

```rust
ctx.cancel.clear();
qaqh_workspace::clear_cancel();     // ← 主动清除取消标志
```

随后 `loop_injection.rs:196-220`（`LoopPhase::Idle` 分支）：

```rust
LoopPhase::Idle => {
    if !self.claim_injection(&injection, &command_id) { return None; }
    // …
    let outcome = self.input.handle_system_input(&mut ctx, &text, ...);  // ← 开新回合
    Some(outcome)
}
```

**没有任何「本会话是否已被用户取消」的检查**。

## 3. 三缺陷如何叠加成「复活」

```text
用户取消父会话
  │
  ├─ 父会话 loop 收到 ConversationCancel → 发 ConversationCancelled
  │     （只作用于父会话自身的回合状态机）
  │
  ├─ ✗ 取消**不传播**到子 seed
  │     （全仓搜 children/descendants/subagent_seeds 的 cancel 传播：零命中）
  │
  └─ 子代理 collector 仍在跑
        │
        ├─ 收到 ConversationCancelled（若子回合也恰好被 cancel）
        │     → did_cancel = true，final_answer = "[SUBAGENT 'x' CANCELLED]"
        │
        └─ 缺陷 2：cancelled 仍注入父会话
              │
              └─ 缺陷 3：注入路径 clear_cancel() + 开新回合
                    │
                    └─ 父会话「复活」：用户以为已取消，模型却又跑了一轮
```

叠加**缺陷 1** 后更糟：子代理因 liveness 未注册而被误封（现象 C），
产生 `cancelled=true` 的假终态；而这个假终态的结果**照样注入**（缺陷 2）。

## 4. 为什么「前端和后端都判定 cancel」却仍复活

| 侧 | 判定依据 | 为何不足以阻止复活 |
|---|---|---|
| 后端 | `did_cancel=true` + `registry_ref.finish()` | `finish` 只写注册表；注入在 `finish` **之前**已发出（lib.rs:543-595 早于 597） |
| 前端 TUI | `ControlEvent::SubagentStatus{state:"CANCELLED"}` → `apply_status` 置 `Cancelled` | 只改 `SubagentEntry.state`；**不停止跟踪**，也不阻止父会话新回合 |

TUI 侧 `apply_status`（`src/app/subagent.rs:207`）只做状态赋值，
`untrack_subagent` 只从 `subagent_seeds` 移除（`subagent.rs:352`）。
**但父会话的 timeline 流仍在**——注入进来的新回合会正常投影到 TUI，
用户看到的就是「已取消的子代理，父会话却又动了」。

## 5. 修复方案

### 5.1 P0：`spawn_subagent_inprocess` 注册 liveness（1 行）

```rust
// registry.rs:361 附近，activity.begin 之后
if let Some(hub) = self.hub.as_ref() {
    hub.mark_worker_live(seed);
}
```

并在子 actor 退出路径（`registry.rs` 的 stopped 分支）调 `mark_worker_dead`。

> **补充发现**：`hub.mark_worker_dead` 全仓**只定义、从未被调用**
> （`grep -rn mark_worker_dead crates/` 仅命中定义处）。`live_workers` 实际只靠
> `hub.forget_seed`（`hub.rs:791-793`）在会话关闭时清理。因此即便补上
> `mark_worker_live`，子代理**正常退出后**仍会滞留在 `live_workers` 里，
> 直到 `forget_seed` 被调——后者是否覆盖子代理路径需一并核实。

**这条修复现象 C**（正在运行的子代理被误封）。

### 5.2 P0：cancel 时不再注入结果

`qaqh-subagent/src/lib.rs:533` 的注入块加守卫：

```rust
if !parent_seed.is_empty() && !did_cancel {
    // …注入…
}
```

**语义**：取消是用户意图，结果不应回灌。若希望「取消也要留痕」，
改为注入一条**纯状态标记**（不带 answer 正文、且明确标注已取消），
而不是完整结果 + 开启新回合。

**这条修复现象 A**。

### 5.3 P1：注入路径尊重会话取消态

`engine_input.rs:261-262` 的 `clear_cancel()` 是有意的（新用户输入应清取消），
但**系统注入不应复用该语义**。建议：

```rust
// handle_system_input 增加参数或区分路径：
// 用户输入 → clear_cancel()（保持现状）
// as_system 注入 → 若会话处于「用户已取消」态，拒绝或延迟
```

需要一个「用户取消」与「回合取消」区分开的标志位——当前 `cancel` 是
单一的回合级标志，语义不足以表达「本会话已被用户放弃」。

### 5.4 P1：父会话取消时传播到子 seed

`ConversationCancel` 处理（`loop_dispatch_conversation.rs:95`）增加子代理清理：
向该会话 spawn 过的所有子 seed 发 `ConversationCancel`。
需要父会话记录自己的子 seed 集合（当前无此登记）。

### 5.5 P2：TUI 侧

- `apply_status` 收到 CANCELLED 后应**真正停止**该 seed 的跟踪（含 timeline 流），
  而非只改状态（否则持续 401 轮询，见现象 B 的 L5882/5893/5913）。
- `mark_subagent_closed` 已在 404 时生效，但 CANCELLED 路径未调用它。

### 5.6 P2：`mark_exited` 状态单调性

`crates/qaqh-workspace/src/process_registry.rs:478`：

```rust
pub fn mark_exited(id: u32, code: i32) {
    if let Some(entry) = r.entries.get(&id) {
        *entry.status.lock()... = ProcStatus::Exited(code);   // ← 无条件覆盖
```

而 `is_running` 的注释（L463-465）声称「status 单调，一旦离开 Running 不会回退」。
`mark_exited` 会把已 `Killed` 的条目改回 `Exited`，**违反该不变量**。
`collect_subagent_result` 的 `registry_ref.finish()`（lib.rs:597）在 cancel 路径
也会走到这里。建议 `mark_exited` 加守卫：

```rust
if matches!(*entry.status.lock()..., ProcStatus::Killed) { return; }
```

## 6. 验证方式

修复后应能在日志中确认：

1. 子代理 spawn 后立即出现 `worker alive for {seed}; skipping bootstrap orphan seal`
   （而非 `sealing orphan active turn`）。
2. cancel 路径下**不再出现** `inject accepted`。
3. 取消后父会话**不再出现**新的 `TurnStart`。
4. 已终态 seed 不再被周期性 `GET .../timeline`（TUI 停止跟踪）。
