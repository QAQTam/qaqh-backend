## 3. 发现 D-1：`tool_outbox_locking` 的并发扩展性断言依赖真实墙钟

### 3.1 现象

全量测试 63 个集成目标中唯一失败项：

```
running 3 tests
test concurrent_sessions_scale_end_to_end ... FAILED
test flush_does_not_serialize_on_a_slow_session ... ok
test flush_is_joined_before_returning ... ok

---- concurrent_sessions_scale_end_to_end stdout ----
thread 'concurrent_sessions_scale_end_to_end' (3050) panicked at crates/qaqh-runtime/tests/tool_outbox_locking.rs:193:5:
8 会话并发追加耗时 157.805239ms，未见扩展（串行下限 512ms）——锁分片或 fsync 批量化未生效
test result: FAILED. 2 passed; 1 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.60s
```

### 3.2 根因（E2）

断言位于 `crates/qaqh-runtime/tests/tool_outbox_locking.rs:193-197`：

```rust
let serial_floor = FSYNC_COST * (PER_SESSION as u32);   // 8ms * 64 = 512ms
assert!(elapsed < serial_floor / 4, ...);                // 阈值 128ms
```

测试意图正确（验证「追加路径不再每条同步 fsync、不再跨会话互斥」），但**判据选了墙钟**。`serial_floor / 4 = 128 ms` 与实测 157 ms 只差 23%，处在任何调度抖动都会被击穿的区间。测试自身在 `:167-171` 已经装了 `fsync` 计数钩子 `hook.hits`，真正稳定的判据就在手边却没用。

### 3.3 影响面

- 不阻塞功能：`flush_does_not_serialize_on_a_slow_session` 与 `flush_is_joined_before_returning` 均通过，被测的锁分片/fsync 批量化行为本身是好的。
- 真实损害是**可信度**：CI 或本地跑出红，容易被误判为本轮改动引入的回归（本仓 N-6 已有同类教训——`todo_contract` 复用数据目录假红）。本仓高度依赖「验收命令原样粘贴」的流水线，假红会直接污染派发结论。

### 3.4 复现（E1）

```bash
export HOME=/home/qaqtamsy RUSTUP_HOME=/home/qaqtamsy/.rustup CARGO_HOME=/home/qaqtamsy/.cargo
cd /home/qaqtamsy/项目/qaqh-backend
d=/home/qaqtamsy/.qaqh-testrun; mkdir -p $d
QAQH_DATA_DIR=$d TMPDIR=$d cargo test -p qaqh-runtime --test tool_outbox_locking
```

期望（当前）：`concurrent_sessions_scale_end_to_end` 在负载下间歇 FAILED，耗时在 128 ms 上下浮动。

### 3.5 修复建议

最小 diff：把判据从墙钟换成已有的 fsync 命中计数。

```rust
// 替换 :193-197 的 assert!
let hits = hook.hits.load(Ordering::SeqCst);
assert!(
    hits <= SESSIONS * 2,
    "追加路径 fsync 次数 {hits} 超预期（{SESSIONS} 会话各一次 flush）——fsync 批量化未生效"
);
```

加固（可选，代价是测试变慢）：保留墙钟断言但放宽到 `serial_floor / 2`（256 ms）并套一层「连续 3 次取中位数」，仅作为回归兜底，不作为主判据。**不建议**单纯把阈值调大——那只是把 flaky 推迟到更慢的机器上爆发。

### 3.6 验收清单

1. `cargo test -p qaqh-runtime --test tool_outbox_locking` 连跑 5 遍 → 5 遍 `3 passed`。
2. 人为在追加路径重新引入 `fsync`（或把 `hits` 阈值改小）→ 新断言必须打红，证明判据有效（防「改完永远绿」的假修复）。
3. `cargo test --workspace --no-fail-fast` → 全绿，0 failed。

## 5. 发现 D-3：`qaqh-config` 反向依赖 `qaqh-workspace`

### 5.1 现象

`crates/qaqh-config/Cargo.toml:28-29`：


### 5.2 根因（E2）

### 5.3 影响面

- `qaqh-workspace` 的任何改动会牵动 `config` / `lsp` / `mcp` / `subagent` 四个下游重编译。
- 概念上 `PermissionLevel` 是**契约词汇**而非工具实现，放在工具层是错位的（对照：`tool_mode` 定义在 `qaqh-types`，见 README §Workspace 成员表）。

最小 diff：把 `PermissionLevel`（`permission.rs:96-106`）连同其 `from` 解析器迁到 `qaqh-types`，`qaqh-workspace` 改为 `pub use qaqh_types::PermissionLevel;` 保持兼容；再删掉 `qaqh-config/Cargo.toml:29`。`ToolCategory` 是否一并迁移可另议——它与工具注册耦合更紧，留在 workspace 更合理。

## 7. 发现 D-5：版本真源与对外 UA 版本号手工维护两处

### 7.1 现象

- `version.txt` = `1.0.1`，`Cargo.toml` `[workspace.package] version = "1.0.1"` —— 二者由 `scripts/sync-version.ps1` 同步，是真源链。
- 但对外 UA 走另一条路：`crates/qaqh-types/src/platform.rs:26` 的 `pub const QAQH_USER_AGENT: &str = concat!("qaqharness/", qaqh_ua_version!(), "/");`，README §版本管理 明确写「在 `platform.rs` 宏内手工维护，与 cargo 包版本解耦（不带 rc/预发布后缀）」。

### 7.2 根因（E2）

UA 版本刻意不带 rc 后缀，与包版本语义不同，故不复用同一真源。这是**有意的设计**，不是 bug；风险在于「手工维护」这一环没有校验。

### 7.3 影响面

P3：发版时若 `version.txt` 升到 `1.1.0` 而 UA 常量未同步，对外 User-Agent 会长期停留在旧版本，影响服务端侧的版本统计与问题定位，且不易察觉。

### 7.4 复现（E2）

```bash
cd /home/qaqtamsy/项目/qaqh-backend
cat version.txt; grep -n 'qaqh_ua_version\|QAQH_USER_AGENT' crates/qaqh-types/src/platform.rs
```

### 7.5 修复建议

最小 diff：写一个单测锁住二者主版本号一致（允许 UA 落后于包的预发布后缀）：

```rust
#[test]
fn ua_version_tracks_package_version() {
    let pkg = env!("CARGO_PKG_VERSION");
    assert!(qaqh_ua_version!().starts_with(pkg.split('-').next().unwrap_or(pkg)));
}
```

加固（可选）：把 `qaqh_ua_version!` 改成从 `version.txt` 由 build script 生成，彻底消灭手工环节。代价是引入 build script，且 `qaqh-types` 目前无 build 依赖。

### 7.6 验收清单

1. 新增单测通过；人为改小 `platform.rs` 里的 UA 版本 → 单测打红。
2. `just sync-version` 后 `cargo test -p qaqh-types --lib ua_version` 仍绿。
