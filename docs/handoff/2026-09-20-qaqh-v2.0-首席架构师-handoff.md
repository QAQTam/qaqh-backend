## 2. 已冻结的架构裁决（不要重新开题）

以下方向已跨 backend、TUI、Codex、Grok 三方交叉，后续修复只允许做一致性收口：

1. 每 session 一条 append-only canonical `events.jsonl`；其他 journal/snapshot/offload 只能是派生缓存。
2. `SessionActor` 是 session 状态唯一 owner；外部只提交 command。
3. `TurnCore` 是纯状态机，不 await、不碰文件/网络/线程/锁。
4. `ToolRuntime` 统一 admit、schedule、sandbox、cancel、audit；loop 不内联工具执行细节。
5. `SessionFact -> ProjectionEvent -> WireEvent` 分层；canonical cursor 为 `(log_id, fact_seq, projection_index)`。
6. 工具默认 at-most-once + reconciliation；`ToolFinished::Indeterminate` 是不可逆终态。
7. `AuditStore` 是独立全局 hash chain，不进入 session projection。
8. v2.0 保留 daemon/TUI 两进程；embedded 单 binary 延后到 v2.1。
9. canonical fact 同版本未知 kind/payload version fail-closed；additive/`Unknown` 只覆盖 wire/display/resource/service。
10. 子代理先做 parent/child edge、supervisor、mailbox、quota；graph scorer/role template 延后。

## 3. 第三轮 NPC 阻断：必须先修

### B1 — `commit/clock` 缺第三态，降级路径会自相矛盾

**问题位置**

- `docs/spec/2026-09-20-session-fact-v2-schema-spec.md` §5.2 第 7、8 条
- `RecoveryOutcome` 当前只有 `writable / read_only_upgrade_required / tombstone`

**反例**

1. 业务 fact `fsync` 成功。
2. `events.commit.json` 更新失败，按第 7 条 session 进入 read-only。
3. 第 8 条要求 clock 只能在 commit marker durable 后推进。
4. 该 session 既不是正常的 `writable`，也不属于 `read_only_upgrade_required` 的“未知版本”语义；没有稳定状态说明谁修复 commit marker、何时恢复 clock。
5. 若误判为 writable，clock/replay window 永远推不动。

**推荐收口**

- 增加明确的第三种恢复状态，例如 `RecoveryOutcome::CommitRecoveryRequired`，或在 spec 中冻结等价的 recovery-only 状态；不要复用 `read_only_upgrade_required` 表达 I/O/commit 故障。
- 明确状态机：
  - `writable`：fact fsync -> commit marker durable -> clock 推进 -> publish/ack。
  - `commit_recovery_required`：只允许 recovery/repair 路径；先验证 committed prefix，修复或重写 commit marker，再回到 writable。
  - `read_only_upgrade_required`：只表示未知 schema/版本，不允许用普通 recovery 自动降级。
- 补充 crash/EIO/commit-marker-write-failure 三组 fixture 与验收。

**Owner**：B（schema/recovery）  
**Gate**：NPC 明确确认第三态和 clock 推进顺序无歧义。

### B2 — `RecoveryStep` 与 `RecoveryAction` 未一一对齐

**问题位置**

- spec §2.5 `RecoveryAction` 表
- spec §6.1 `RecoveryPlan` / `RecoveryStep`
- spec §6.2 恢复矩阵
- spec §6.5 recovery fact 幂等表

**问题**

本 PR 新增了：

- `RecoveryStep::TurnStarted`
- `RecoveryStep::SubagentFinished`
- `upgrade_superseded` action

但 `RecoveryAction` 表没有同步 `turn_started`、`subagent_finished`。而 `SessionRecovered.actions` 被定义为“同一 recovery batch 已写 facts 的摘要”，下游无法判断哪些 step 必须进 actions、哪些可以省略。

**推荐收口**

- 给 `RecoveryAction` 补齐 `turn_started` 与 `subagent_finished`，字段分别与对应 step 对齐。
- 明确规则：所有 `RecoveryStep` 必须映射到恰好一个 action，或显式列入“不产生 action”的白名单。
- 同步 §6.1、§6.2、§6.5，保证 step、action、幂等键三张表一一可查。

**Owner**：B（schema/recovery）  
**Gate**：用一张 step/action 对齐表或规范句消除歧义。
