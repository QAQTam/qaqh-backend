1. 触发机制

根因位于 crates/qaqh-gate/src/chat_sdk.rs：split_inline_thinking（原 65–85 行）是一个跨整个请求的有状态机， 在 consume（原 621 / 639 行）里对每一个 SdkEvent::TextDelta（即 content 正文）无条件运行， 无 provider 门控、无跨 delta 标签拼接缓冲。marker 写死为 <think> 与 </think>。

  • 命中开标记即把 in_thinking 翻为 true，此后所有正文经 push_reasoning 发成 ReasoningDelta；正文里几乎不会有配对的闭标记，状态卡死 → 表现就是「最后一段像是在思考链里说完的」。
  • 标记是固定字面量，但函数每次只看单个 delta：闭标记一旦被 SSE 切成两帧就识别不到，状态同样卡死；这解释了现象的偶发性 / 边界相关。
  • 注释自称 "compatibility guard"，实际却对所有 Chat Completions 端点的所有正文生效。

最小复现（精确复刻该纯函数，node 跑的，未编译仓库）

场景落到【正文】落到【思考链】结束态
A：正文里引用该字面量（不闭合），之后继续正常输出 "用法示例：在配置里写 " " 即可开启思考模式。 然后这里是正常的收尾正文，一直到本句结束。" inThinking=true（卡死）
B：闭标记被切成 </thi + nk> 两帧 "先想一下" "内部推理过程</think> 之后本该是正文的全部内容以及后续第二帧正文" inThinking=true（卡死）

两种场景都稳定把后续正文灌进思考链，远端完全没参与 —— 纯本地字符串处理。

完整链路（为什么是持久泄露，不只是显示错）

远端 content delta
  → gate consume: 状态机翻转 → ReasoningDelta          ← 错在这里
  → sdk_common.rs finalize(94-99): 按 reasoning/text 缓冲分别建 ContentBlock::Reasoning / Text
      → Done.raw_message 里这段落成思考块（回放历史也错）
  → provider_job.rs(269-281): 完全信任 gate 分类、无二次纠正 → publish_block(Reasoning)

现有测试 inline_think_tags_split_across_chunks（原 916 行）只测了「标签完整闭合」的正向场景，没有覆盖「正文里出现该字面量却不闭合」与「标签被切块」，所以这个洞一直没人踩到。

为什么排除「远端切通道」

  • 真·思考通道是字段级的：chat_profile 的 aliases.response_text = [reasoning_content, reasoning, thinking, analysis_content]，由 SDK 解析成 SdkEvent::ReasoningDelta（原 654 行）如实转发。
  • 远端按生成阶段 / 协议决定把字节放 content 还是 reasoning_content，不会因为「看到自己输出的某个语句」而切换字段。
  • 全仓唯一「看到某个字面量就改变后续分类」的代码就是这个状态机，与现象严丝合缝。
  • 影响范围仅 Chat Completions wire（/chat/completions 全部端点）；messages / responses / gemini 三条 wire 没有这层标签切分。
一把区分的取证方法：用 scripts/wire-capture-proxy.mjs + crates/qaqh-gate/examples/gate_wire_probe.rs（QAQH_GATE_PROBE_WIRE=chat）同时抓「上游回了什么字段」与「gate 发了什么 StreamEvent」。 gate bug：上游始终在 delta.content 输出，但 gate 出 ReasoningDelta，且泄露起点那一句含该字面量 → 字段 / 事件错配。 远端切通道：上游字段本身变成 delta.reasoning_content（或 Responses 的 reasoning item），切换点与「某个语句」无关。
